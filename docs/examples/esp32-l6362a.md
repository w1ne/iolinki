# ESP32-C3 with STEVAL-IOD003V1 / L6362A

This experimental customer reference runs the shared counter/button/LED
application on **ESP32-C3-DevKitM-1 (ESP32-C3-MINI-1)** with native
ESP-IDF 5.4.0. Wi-Fi and Bluetooth are not initialized. It is not a certified
IO-Link device. Hardware timing, master interoperability and the **actual
ESP-IDF firmware LabWired twin including analog C/Q are pending**. A native
host test or an STM32 UART fixture cannot establish this ESP32 twin result.

## Power and jumpers

Power the DevKit through its USB connector. Supply STEVAL CN1 pin 1 (L+)
and pin 3 (L−) from the IO-Link master. Connect DevKit GND to CN6 pin 6 or 7
(common L−). Never connect 24 V to the MCU. The L6362A regulator is a
small-current regulator (12 mA minimum short-circuit threshold at 3.3 V),
not an ESP32 power supply. See [L6362A tables 3 and 13](https://www.st.com/resource/en/datasheet/l6362a.pdf).

Use these solder bridges, with both boards unpowered:

| Item | Setting for this firmware |
|---|---|
| SW1 | Close 1–4, 2–4 and 3–4: OUTH, receiver and OUTL connected to C/Q |
| SW2 | Close 2–3, open 1–2: 3.3 V logic |
| SW3 | Close 2–3, open 1–2: MCU controls EN |
| JP1 | Closed: OUTL path |
| JP2 | Open: auxiliary DI/DQ unused |
| JP4, JP5 | Open: disconnect L78L12 input and VIN output |
| JP3 | Closed **only after JP4 and JP5 are open**: PHY regulator powers shield logic rail |
| JP6 | Open: reset pull-up unused |
| R102 | Remove default 100 Ω IN1-to-3V3 link; hardwire IN1 to shield GND |

Do not join the independently powered DevKit 3V3/5V rails to the shield
3V3/VIN rails. Verify IN1=0 V and shield VDD≈3.3 V before attaching logic
signals. These settings follow [ST UM2424, tables 7–8 and IN1 note](https://community.st.com/ysqtg83639/attachments/ysqtg83639/interface-connectivity-ics-forum/10620/2/en.DM00510917.pdf).
IN1 low is an intentional board modification: the stock board ties it high.

## Logic wiring

| DevKit signal | STEVAL connector/net | Default link |
|---|---|---|
| GPIO4, UART1 TX | CN5 pin 3 / D10 / IN2 | R101 |
| GPIO5, UART1 RX | CN9 pin 3 / D2 / OUT I/Q | R103 |
| GPIO6, EN output | CN5 pin 2 / D9 / EN | R109, then R10 (330 Ω) to EN/DIAG |
| GPIO7, OL falling IRQ | CN5 pin 5 / D12 / OL | R105 |
| GPIO10, DIAG input | CN8 pin 3 / A2 / DIAG | R104 |
| GPIO0, button input | External normally open button to DevKit GND | Internal pull-up |
| GPIO1, LED output | External LED anode via 1 kΩ; cathode to GND | Active high |
| GND | CN6 pin 6 or 7 | Common logic ground |

Connector numbering is from [ST schematic figures 1–2](https://www.st.com/resource/en/schematic_pack/steval-iod003v1_schematic.pdf).
The EN connection must retain R10: EN/DIAG is a bidirectional open-drain
diagnostic node; DIAG is sampled on the IC side, not the MCU output side.
Keep the shield's OL pull-up. CN1 pin 4 goes to master C/Q; pin 2 and pin 5
are unused in this three-wire reference. CN11 is a sensor/I²C header,
not the UART connector.

The chosen MCU pins are exposed on this exact DevKit. GPIO2/8/9 are boot
straps and GPIO8 also drives its RGB LED; GPIO12–17 are flash-related.
GPIO18/19 are USB and GPIO20/21 are the programming/console UART, all
avoided here. GPIO4–7 overlap external JTAG, so use USB debug or disconnect
JTAG when running this wiring. See the [Espressif board pin tables](https://documentation.espressif.com/esp-dev-kits/en/latest/esp32c3/esp32-c3-devkitm-1/index.html).
Other C3 boards need a separately reviewed pin map.

## Build and flash

Install PlatformIO Core, then from the repository root:

```sh
platformio run -d examples/esp32_l6362a
platformio run -d examples/esp32_l6362a -t upload --upload-port /dev/ttyUSB0
platformio device monitor --port /dev/ttyUSB0 --baud 115200
```

`platformio.ini` pins platform 6.10.0 and framework package 3.50400.0
(ESP-IDF 5.4.0). The build produces `.pio/build/esp32c3/firmware.elf`
and `firmware.bin`; upload uses the board bootloader and flash layout.
The included top-level/main CMake files also allow `idf.py set-target
esp32c3 build flash` after sourcing an ESP-IDF 5.4.0 environment.

## Behavior and limits

`main/main.c` uses the current stack APIs and the shared `reference_device`.
Every 10 ms input is `[counter_hi, counter_lo, button]`; output byte bit 0
drives the external LED. The counter wraps at 65535. ISDU identity reads
use the shared device-info implementation. Replace experimental VendorID
1234 / DeviceID 5678 and identity strings in `reference_device.c`, then
update your IODD and master's PD layout before product use.

UART1 uses 8 data bits, even parity and one stop bit. Driver interrupts feed
a 512-byte RX ring with a 32-event queue. Overflow, parity, framing and break
events discard the uncertain frame and return an error. TX enqueue and final
stop-bit waits are bounded by 11 bits/byte plus 3 ms; EN drops before echo
cleanup and receive interrupts are rearmed. A timeout latches a transport
fault until reboot, forbidding all later EN assertions so pending UART bytes
cannot escape on a later frame. UART1 has a single writer, the protocol task;
no other task or ISR may call its TX APIs (the IDF API uses an internal mutex).
IN1=0 makes IN2 TX and OUTI/Q RX noninverting, per ST tables 14–15.

OL means current limitation and can indicate a wake request while SIO drives
C/Q. It does not prove a short-circuit cause. The portable driver reports
EN/DIAG as unavailable while EN is commanded low; asserted DIAG while
enabled aggregates UVLO, overtemperature and cut-off. No individual cause
is guessed. `board_overload` and `board_phy_fault` are available in a debugger;
the latter is normally −1 during receive because EN is low.

Time uses `esp_timer_get_time()` in microseconds; critical sections use
FreeRTOS interrupt-safe spin locks. NVM hooks return **−1**, explicitly
unsupported: synchronous flash erase/write stalls this single core and needs
a deferred persistence design. Idle work is permitted in SIO; SDCI reserves
this single core for a busy protocol loop, with watchdog disabled and no
scheduled millisecond sleep. Response timing at every COM speed must still
be measured on hardware before any timing claim. Portable PHY tests cover
polarity, receive state,
bounded-adapter failure return and diagnostics; they do not test physical
C/Q voltage, ESP-IDF execution or certification.

The portable `test_tx_guard.c` runs the exact firmware transport sequencing
helper against a deterministic FIFO/clock. It checks final-stop-bit ordering,
EN low before echo cleanup/RX rearm, permanent timeout disable and a stalled
FIFO deadline. It also checks RX error stickiness, queue saturation and
valid-byte reads. Run it without any ESP-IDF SDK:

```sh
cc -std=c11 -Wall -Wextra -Werror examples/esp32_l6362a/test_tx_guard.c \
  examples/esp32_l6362a/main/tx_guard.c examples/esp32_l6362a/main/rx_guard.c \
  -o /tmp/test-esp32-tx
/tmp/test-esp32-tx
```
